# Below 10 ms per force at N = 2x10^5: the sub-10 ms record (2026-09-11, in progress)

Plan: `~/.claude/plans/sub-10ms-fmm-200k.md`. Target: jz-fmm's single-A100 front (measured on OUR IC below).
Every timing here is from an idle A100 (`common/gpu_guard.py`), N = 2x10^5 Plummer (seed 0, masses 1/N, G = 1,
softening 1e-7), error = aggregate relative L2 against an fp64 direct sum on 4096 targets (seed 12345). Harness:
`Odisseo-bench-multigpu/benchmark_multigpu/codes/{jzfmm_force_eval,smallleaf_baseline,sub10ms_fronts,probe_*}.py`;
raw rows in `artifacts/sub10ms/` and `artifacts/jzfmm/`; fronts in `artifacts/smallleaf/fronts_2026-09.{json,png}`.

## Phase 1.2 -- the MAC tested the wrong geometry (fixed), and the near volume is the tree

**Defect.** The walk tested `(r_A + r_B)^2 <= theta^2 d^2` with bounding-box centres and half-diagonals while the
real-basis expansions (P2M/M2M/M2L/L2L/L2P) are about the centres of mass. About the COMs the accepted far pairs
reached convergence ratios of 1.56 at theta 0.6 (0.6 % of pairs >= 1), 2.38 at 0.8 (8.6 %), 4.84 at 1.0 (35 %):
divergent expansions. Symptoms: aggL2 flat in p at theta 0.8 (5.3e-3 / 4.1e-3 / 3.5e-3 for p 4/5/6) and RISING at
theta 1.0 (1.7e-2 / 1.8e-2 / 3.7e-2). Fix: `jaccpot/runtime/_mac_geometry.py` (`JACCPOT_STATIC_STRICT_FUSED_MAC_GEOMETRY=com`,
exact COM radii by default; the child-sphere bound costs 2.7x far pairs). After: theta 0.8 p4/5/6 = 2.06e-3 / 1.02e-3 /
5.9e-4 at 47.9 / 56.4 / 61.2 ms (monotone), theta 0.6 p6 8.3e-5 at 85 ms. Front unchanged in time: near share still
0.12 N at theta 0.8 (jz-fmm 0.0116 N).

**Why the volume:** 341 of 3125 radix leaves with radius > 4x median (11 % of particles) sit in 56 % of the direct
volume -- 64-particle Morton BUCKETS in the r ~ 3-5 shell straddle several cells; the top 1 % of leaves are neighbours
of every row. jz-tree's leaves are Morton CELLS. The same walk (COM, exact radii) on cell leaves
(`probe_tree_volume.py`, Karras radix over the cell codes):

| leaves | direct share th0.8 | far pairs (dir) th0.8 | direct th0.6 | far th0.6 |
|---|---|---|---|---|
| radix buckets 64 (3125) | 0.1225 N | 565k | 0.236 N | 1.02M |
| radix buckets 32 (6250) | 0.061 N | 1.17M | 0.121 N | 2.35M |
| **cells 64 (10956, occ 18.3)** | **0.0052 N** | 690k | 0.0129 N | 1.58M |
| cells 32 (20701, occ 9.7) | 0.0019 N | 1.21M | 0.0051 N | 2.78M |
| cells 16 (40972, occ 4.9) | 0.0008 N | 2.08M | 0.0018 N | 4.77M |

Cells inside the fused lane's fixed balanced bucket structure give the same near volume but 2.3x the far pairs (1.59M),
so the Karras structure over the cells is the one built. Padding leaves (one centre, radius 0) MUST be dead in the walk:
unmasked they made 30M near edges. yggdrax's "adaptive octree" mode makes buckets, not cells.

## Phase 1.5 result and Phase 3 -- cell leaves + CSR near field + per-level Pallas cascades

First cell-leaf step (cells64 th0.8 p5, COM MAC): forces correct, eval-only 27.4 ms on the rectangle near-field
kernel because one far-out cell neighbours 10950 of 10956 leaves (rectangle = 99 % padding); the CSR row-chunk kernel
(`JACCPOT_NEARFIELD_LEAFPAIR_CSR=1`) brings the eval to 11.7 ms. The step, however, was 248 ms: the Karras tree over
cell leaves is 40 levels deep (buckets: 13) and every nodes x depth loop paid for it -- attribution integrator 0.6 /
tree 14.7 / upward 90 / downward 136 / near 6.8.

Fixes, all committed on `perf/sub10ms-lanes` (jaccpot) and `perf/pallas-mutual-walk` (yggdrax):

| item | before | after |
|---|---|---|
| exact COM radii: scatter-max -> one-hot segmented scan | 44 ms | ~2 ms |
| cell partition: 2 searchsorted per level -> prefix/suffix scans | 14.1 ms | 1.2 ms |
| M2M / L2L level loops: every internal node -> widest level | 66 / 44 ms | 35 / 43 ms |
| **Phase 3: M2M / L2L as one Pallas launch per level** (`cascade_real_level.py`) | 35.5 / 42.8 ms | **7.4 / 8.5 ms** |
| box geometry deferred under the COM MAC | 1.5 ms | 0 |

**Step: 248 -> 137.6 -> 55.8 ms, launches 23k -> 4,244, aggL2 1.2691e-3 unchanged** (the Pallas cascades and the
loops give identical forces). Remaining stages: M2L CSR 9.4, M2M 8.5 (47 launches), near 6.0, L2L 4.4, eight
`input_transpose_fusion` 8.7 (being attributed), walk + list building ~25.

Kernel notes. The M2L CSR kernel's alignment rotation ``T = B Dz(-ax) B Dz(az)`` is NOT orthogonal, so M2M rotates
back with the per-degree inverse blocks (``T^-1``) and L2L rotates in with ``T^-T``; the z-shift cores are triangular
degree-by-degree ``dz^k/k!`` matrices built from one-hot tables (Triton lowers no gather). Trap: the Karras tree over a
padded leaf set has extra level-0 "roots" (empty padding nodes whose ``parent`` is -1 while the child arrays point at
them); a child-driven L2L and a parent-driven one therefore differ on those empty nodes only -- harmless for forces.

## Phase 2 -- the walk as one Pallas launch per round (`jaccpot/pallas/mutual_walk_pallas.py`)

One `pallas_call` per wavefront round: a block of 64 queue pairs per program (2 warps), MAC + emit + refine in
registers; one atomic per program claims a run of slots in the far / near / next-queue buffers and an in-block
prefix sum hands them out; masked-out lanes store PAST the buffer (a shared in-range dummy index collides with a
real write in interpret mode); empty blocks exit at the top; four rounds run per `while_loop` check (each check
copies the predicate to the host); the three overflow flags have one counter each (an OR of bits under
`atomic_max` let a later queue overflow erase an earlier far overflow). Same pair SETS as yggdrax
`dual_tree_walk_mutual` on bucket and cell trees (`tests/unit/runtime/test_mutual_walk_pallas.py`), same flags.

N = 2e5 cells64 th0.8 (71 rounds, peak wavefront 85,598, far 345k canonical, near 186k): **2.3-3.5 ms vs 11.4-16.9 ms
for the flat walk** (the spread is the machine: 30-40 host load, every other card busy); GPU time of the 72 round
launches is 0.95 ms/step, the rest is the loop's host round trips. Wired behind
`JACCPOT_STATIC_STRICT_FUSED_WALK=pallas`; the emission order is atomic order, so the far list is sorted by (a, b)
and the near rows by (target leaf, source) -- one composite int32 sort when the bounds fit, two stable sorts
otherwise -- which costs 0.1 ms/step (`..._WALK_DETERMINISTIC=0` A/B: 29.36 vs 29.46 ms).

The trace of the step with the Pallas walk then showed the per-level M2M / L2L launches costing 180 / 94 us EACH:
the grid is the widest level's width for every level and every program ran the whole translation (writing a dead
row when its slot was past the level's count). `pl.when(slot < count)` before the table loads: 47 M2M launches
8.4 -> 1.2 ms, 47 L2L 4.4 -> 0.7 ms.

**Step (cells64 th0.8 p5, COM exact, CSR near, Pallas cascades + P2M + walk): 47.1 -> 41.5 -> 29.5 ms/step,
launches 4,160 -> 1,819, aggL2 1.2691e-3 unchanged** (`artifacts/sub10ms/jaccpot_cells64_th0.8_p5_pwalk2.json`).
GPU busy 28.1 of 29.5 ms: the step is now compute-bound. Per step: M2L CSR 9.37 / near CSR 5.97 / three XLA
scatter fusions 1.79 + 1.34 + 0.81 (the near kernel's per-chunk partial reduce is one of them: 32,768 chunk rows x
64 x 4 fp64 = 64 MB through `segment_sum`) / M2M 1.24 / walk rounds 0.95 / L2L 0.71 / sorts 0.76 / memcpys 1.0.

## Phase 5 -- M2L: the kernel is per-pair-latency bound, not row bound

Far rows on this tree: 21,885 live of 32,767, mean 31.6, p99 91, max 762 (level-15 node); near rows: mean 34,
max 10,950 (the far-out cells). Synthetic lists through `m2l_real_csr_pallas` (order 5, fp32, random sources):
21-25 ns/pair for uniform rows of 5, 21, 84, 337 or 1348 pairs, for one or 32 rows of 762 among rows of 21, and
for 1, 2, 4 or 8 warps -- i.e. THROUGHPUT-bound at ~14 us per pair-iteration per program, about 6 programs per
SM. Row chunking (the Phase 4.1 cure) would buy nothing here. The per-pair chain is 9 reductions over
`(Bp, Wp, Wp)` = 2048-element broadcasts (four `B` applications, four `Dz`, the z-core) for ~20 kflop of useful
work: the rewrite is a tile of K = 16 source pairs per iteration with per-degree `(K, Wp)` tiles and
`(16, 16) @ (16, 16)` dots (`precision=HIGHEST` -- the Triton lowering maps DEFAULT fp32 dots to TF32).

**Phase 5 result.** Three kernels for the same real M2L over the target CSR (order 5, fp32, A100, synthetic rows
with the real list's shape -- gamma rows, mean 32, max 215):

| kernel | layout of one pair | ns/pair | notes |
|---|---|---|---|
| per-pair (`m2l_real_csr.py`) | ``(Bp, Wp)`` tile across the program, 9 broadcast reductions | 24 (13.6 on the real list) | latency of the reduction chain |
| tiled (`m2l_real_csr_tiled.py`) | K=16 pairs, per-degree ``(K, Wp) @ (Wp, Wp)`` dots | 8.5-11.7 | SAME speed with IEEE and single-pass TF32 tensor-core dots: not the arithmetic |
| **lanes (`m2l_real_csr_lanes.py`)** | **one pair per thread, 36 registers, rotation matrices as immediates, no cross-lane traffic until the final reduce** | **1.3 (k32, 1 warp)** | 18x; fp32 deviation 6e-7 |

The tiled kernel in the step: M2L 9.4 -> 4.3 ms, step 27.9 -> 20.8 ms (with the scatter fixes below). Selector:
`JACCPOT_M2L_CSR_KERNEL=pair|tiled|lanes` (`_LANES`, `_WARPS`, `_TILE`, `_DOT` tune).

**Scatters (found by HLO dump, `--xla_dump_to`):** the 1.3 ms `s32[32767]` scatter-add was `csr_by_target`'s
`segment_sum` counting sources over the 2^21 far entries (now a `searchsorted` on the sorted key); the 1.8 and
0.8 ms `f32[200000,3]` scatter-adds were the near-field and L2P leaf-slot assemblies whose PADDED slots (800k of
1M on a capacity-padded cell tree) all carried one index and serialised XLA's atomics on that address (masked
slots now point past the buffer, `mode="drop"`, the L2P ones also `unique_indices`). Scatter stage 4.3 -> 0.4 ms.

**Step with the lane M2L (`JACCPOT_M2L_CSR_KERNEL=lanes`): 16.8 ms/step (spread 42 %: 28 host load, every other
card busy), M2L 9.4 -> 0.19 ms, aggL2 1.2691e-3 unchanged, 1,905 launches**
(`artifacts/sub10ms/jaccpot_cells64_th0.8_p5_pwalk5.json`). GPU busy 15.2 ms: near CSR 6.0 / Pallas cascades +
walk + P2M ("other") 3.2 / XLA fusions 1.9 / 347 small D2D memcpys 1.2 (the walk's while loop) / sorts 0.84 /
reduce 0.35 / scatter 0.36 / gather 0.29 / M2L 0.19.

## Phase 4.2 -- the near field on sparse cell leaves

Cell leaves hold 18.3 particles on average in 64 slots. The CSR leaf-pair kernel looped over all 64 source slots of
every neighbour (3.5x masked-zero iterations) and ran the whole source loop for the second 32-wide target subtile
of leaves that have no particle there (most). Per-leaf occupancy (one past the last live slot) now bounds the
source loops -- the skipped slots contributed exact zeros, so the float32 sums are bit-identical -- and a program
whose subtile starts past the count writes zeros and exits (`pl.when`).

**Near result: 6.0 -> 1.8 ms; step 14.8 ms (GPU busy 11.0), aggL2 1.2691e-3 unchanged**
(`jaccpot_cells64_th0.8_p5_pwalk6.json`). 1,905 launches for 11 ms of GPU work leave ~4 ms of launch gaps on a host
at load 25-28; the walk's `while_loop` alone copied its 19 carried buffers per iteration (347 D2D memcpys/step) ->
16 rounds per check.

## Phase 6 -- defaults, the first front rows, and an open crash

cascades, the Pallas walk and the lane M2L are on; the COM MAC is the default everywhere. Explicit spellings keep

p4 th0.8 12.95 @ 1.1e-3, p4 th1.0 12.0 @ 1.8e-3, p5 th1.0 12.7 @ 9.7e-4 -- their 114 launches gain nothing from graphs.
